# ファームウェア LUKS 鍵の解析と回収

## この文書の位置づけ

CDJ-3000 と CDJ-3000X のファームウェア更新ファイル（`.UPD`）を復号する鍵の解析結果と、実機からの回収手順をまとめる。
結論を先に述べる。
`.UPD` は標準的な LUKS1 コンテナで、これを開ける鍵は約 32 バイトのランダムなバイナリ鍵ファイルである。
そのため `.UPD` 単体からの総当たりによる鍵回復は、数学的に不可能である。
鍵は実機の非暗号領域に存在し、実機を root 化して吸い出すのが唯一の現実的な経路である。
なお LUKS ヘッダを版間で比較したところ、CDJ-3000X は 3 バージョンで master key が同一であることが数学的に確定した（後述）。CDJ-3000 も同じ運用の可能性が高いが、こちらは実機から鍵を得たうえで確認する必要がある。

## UPD の暗号構造

`.UPD` の先頭には LUKS1 のヘッダがあり、ファイル全体が一つの LUKS コンテナになっている。
解析で判明したパラメータは次のとおり。

- **暗号**：AES-256、モードは `xts-plain64`
- **ハッシュ**：`sha256`（PBKDF2 と AF マージに使用）
- **マスターキー長**：64 バイト（AES-256-XTS のため 32 バイト鍵が二本）
- **有効キースロット**：スロット 0 のみ、PBKDF2 反復は約 134 万回、残り 7 スロットは無効
- **UUID**：`9424e626-da90-4eb0-a72f-a1a32e8326e0`

ペイロードは 2 MiB のヘッダ領域の後ろに続き、全体のエントロピーは約 8.0 bit/byte である。
これは正しく暗号化された領域の値で、平文への近道や実装上の弱点はない。
唯一の非暗号領域は、ファイル末尾の 15 バイトのトレーラで、ASCII の "XDJ-RR3.22" を含む。
このトレーラの存在は、別のリバースエンジニアリング記録（dnewcome/reversing）の記述とも一致する。

## 鍵の正体と総当たりが成立しない理由

エミュレータの Install Firmware ウィザードは、鍵を生バイナリの鍵ファイルとして直接読み込む。
入力欄の例示は `aes256.key` で、内部では `LuksKey::from_file` がファイルの生バイトをそのまま PBKDF2 に渡す。
つまりスロット 0 を開ける「パスワード」の実体は約 32 バイトのランダムなバイナリであり、人が入力するパスフレーズではない。

この事実が総当たりの可否を決める。
辞書攻撃ツールが試すのは印字可能な文字列であり、ランダムなバイナリ鍵はその探索空間に含まれない。
当たり得るのは 2^256 通りのバイナリ全体で、これはどんな計算資源でも走査しきれない。

## 鍵はどこにも公開されていない

同種のリバースエンジニアリングプロジェクトを調査したが、鍵を公開しているものはなかった。

- **dnewcome/reversing**：`.UPD` を「LUKS1（AES-XTS-plain64、512 ビット鍵）と 15 バイトの非暗号トレーラ」と記述し、「64 バイト鍵の入手が唯一の障壁」とする。鍵は載せていない。
- **emmaworley/cdj3k-root**：CDJ-3000 を root 化して SSH を通すプロジェクト。ビルドに鍵が要るが「入手方法は提供しない」とする。
- **OllieCross/CDJ_DJM_Emulator**：暗号ブロブを解かず、クリーンルーム実装で回避する方針。

Web 全体でも、鍵の流出や配布は確認できなかった。

## バージョン間の鍵同一性

AlphaTheta 公式が配布する両機種の全バージョン（CDJ-3000 は v1.10 から v3.22 の 9 版、CDJ-3000X は v1.10、v1.20、v1.40 の 3 版）を取得し、それぞれの LUKS1 ヘッダから cipher、mode、hash、UUID、mk_digest、mk_salt、mk_iter、slot0 iterations を抽出して比較した。
以下は `tools/key-recovery/luks_header_diff.py` で再現できる結果である。

### CDJ-3000X の 3 バージョンは master key が同一

以下のフィールドが全 3 版で完全一致した。

- UUID：`fa03960e-420a-4044-8bfe-7abbe5f23daf`
- mk_digest：`332fb7805b65e359d1e291e7ca6d7f115148744d`
- mk_salt：`4e5068221c998b3e313bd326727d781feee6a90eb1d58f10e314ce267218b216`
- mk_iter：178086
- slot0 iterations：2849390

mk_digest は `PBKDF2(master_key, mk_salt, mk_iter)` の出力であり、salt と iter と digest が同一なら master key も同一である（PBKDF2 は決定的関数のため）。
したがって Pioneer は CDJ-3000X の全バージョンで同じ LUKS ヘッダを再利用し、ペイロードだけを差し替えている。
1 個の `aes256.key` を得れば v1.10、v1.20、v1.40 のすべてが復号できる。

### CDJ-3000 は各版で LUKS ヘッダを新規生成

9 版すべてで UUID、mk_digest、mk_salt、mk_iter、slot0 iterations が異なった。
一方 cipher、mode、hash、key_bytes はすべての版で一貫している（AES、xts-plain64、sha256、key_bytes=64）。
これは Pioneer が版ごとに `cryptsetup luksFormat` を新規に実行していることを意味する。

ヘッダのみからは、passphrase として使われる `aes256.key` が全版で同一かは判定できない。
ただし cdj3k-root のビルド運用が単一鍵前提であること、CDJ-3000X の実装が「機種ごとに 1 鍵」の設計思想を示していることから、CDJ-3000 も同一鍵で運用されている可能性が高いという見立ては維持できる。
実機から鍵を抽出したのち、`.tmp/firmware/CDJ-3000/*.UPD` に対して `keyhunt --dir` を実行すれば、この仮説を直接検証できる。

## 実機からの鍵ダンプ手順

実機（root 化済み）から鍵を吸い出すのが本命の経路である。
優先度の高い順に示す。

1. **root SSH からファイルを直接取得**：eMMC 上の rootfs は非暗号なので、`aes256.key` を rootfs から吸い出す。
2. **dmsetup によるマスターキー露出**：更新時に LUKS が開いている隙に `dmsetup table --showkeys` を実行し、マスターキーを 16 進で得る。
3. **UART シリアルコンソール**：RK3399 近傍の端子に 115200 8N1 で接続し、更新中の `cryptsetup luksOpen --key-file` の引数を観測する。
4. **JTAG によるメモリダンプ**：更新中の RAM を取得し、鍵を探す。

root 化そのものは emmaworley/cdj3k-root の方式で行える。
FAT32 の USB に更新ファイルと `authorized_keys` を置き、通常のファーム更新を走らせると SSH root が開通する。
作者がビルド済みのリリースを配布しているため、鍵がなくても root 化だけは可能である。
ただし配布物は特定のファームバージョン向けなので、機体のバージョンに合わせる必要がある。

## 鍵ファイルとマスターキーの区別

回収時に、二種類の異なるものを混同しないよう注意する。

- **鍵ファイル**：スロット 0 を開ける `aes256.key`、約 32 バイト。エミュのウィザードが要求するのはこれである。
- **マスターキー**：`dmsetup --showkeys` で得られる 64 バイトの値。ペイロードを直接復号できるが、ウィザードには入力できない。

実機からは鍵ファイルの実体を吸い出すのが本命である。
マスターキーしか得られない場合は、`cryptsetup open --master-key-file` に相当する経路で `.UPD` を直接復号する。

## 回収・検証ツール

この経路を支援するツールを `tools/key-recovery/` に置いた。

- `collect_cdj3k_key.sh`：実機 root 後に実行する鍵コレクタ。`dmsetup --showkeys`、更新スクリプト内の `--key-file` パス検索、鍵ファイル候補の収集を行い、一つのアーカイブにまとめる。
- `keyhunt-src/`：検証オラクル。リポジトリ本体の復号コードで候補鍵を検証するため、暗号の再実装による誤判定がない。`--dir` モードで、回収した候補ディレクトリを一括検証する。
- `luks_header_diff.py`：複数の `.UPD` の LUKS1 ヘッダを抽出して並べる比較ツール。前述の版間解析を再現できる（PEP 723 のインラインスクリプトとして書かれており、`uv run` で実行）。
- `README.md`：root 化から収集、検証までの手順。

一致した場合は `aes256.key` を出力し、復号済み ISO を書き出す。
その鍵ファイルを保存すれば、エミュのウィザードにそのまま使える。
